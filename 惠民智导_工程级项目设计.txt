4. 最危险的五个失分点

（1）被评委认为只是“政务问答机器人”。
应对：核心演示必须是资格预筛、缺口解释、材料校验和组合救助，不是开放式闲聊。

（2）与现有“社会救助一件事”重复。
应对：现有官方平台侧重申报和联办，本项目定位为申请前的“发现—理解—预筛—备料—分流”辅助层，帮助用户知道自己该办什么、缺什么、为什么；系统最终把用户引导到官方渠道，不替代官方系统。

（3）大模型引用旧政策或生成错误结论。
应对：资格判断由版本化规则引擎完成，大模型只负责意图理解和自然语言解释；所有结论必须绑定有效日期、条款和链接；冲突或缺失时拒答并转人工。

（4）没有真实应用证据。
应对：尽早联系1—2个社区、社会工作服务站、法律援助机构或校内社会工作教师，做需求访谈和小规模试用。国赛阶段至少要有签字/盖章的试用反馈、访谈纪要或合作意向之一。

（5）采集困难群众敏感信息，造成合规风险。
应对：训练只用公开政策和合成家庭案例；真实材料默认端侧处理、脱敏、短期保存；公开演示使用虚构人物；系统明确“不具有行政审批效力”。

二、项目一句话定义与价值主张
============================================================

1. 一句话定义

面向困难群众和基层工作人员，输入自然语言描述或家庭基本情况后，系统在指定地区和日期下，自动匹配可能适用的救助项目，给出可解释资格预筛、缺失条件、材料清单、办理路径和官方依据，并对上传材料进行完整性与一致性预检查。

2. 核心价值

对群众：从“不知道能申请什么”变成“一次描述，得到组合式导办清单”。
对基层：从人工翻找多份政策变成“规则结论 + 原文证据 + 待核问题”。
对管理者：从政策发文后难以追踪影响变成“版本可追溯、规则可测试、更新可预警”。

3. 系统不是做什么

（1）不替代政府部门审批；
（2）不保证一定获批；
（3）不代替法律意见；
（4）不直接连接或修改政府业务系统；
（5）不收集不必要的真实身份证、银行卡等信息；
（6）不对未收录地区输出强确定性结论。

三、目标用户、痛点与真实需求验证
============================================================

1. 目标用户

U1 困难群众及家属：不了解政策术语，可能不熟悉复杂网页，关心“我能不能办、去哪办、带什么”。
U2 社区/街镇工作人员、社工：需要快速了解家庭情况、检索条款、发现缺失材料，同时承担解释责任。
U3 政策维护人员：需要及时发现政策过期、替代关系和规则冲突。

2. 待验证痛点假设

H1：群众不知道救助事项全貌，容易只申请已听说的一项而遗漏关联救助。
H2：政策分散于多个部门和年份，收入、财产、家庭成员、刚性支出等概念难理解。
H3：材料准备不完整或信息矛盾会增加往返和咨询成本。
H4：基层人员需要为建议提供可追溯依据，不能只相信模型生成内容。
H5：政策更新后，通用搜索和普通RAG可能继续返回旧规则。

以上都属于“待验证假设”，不能直接在作品里写成已证实事实。

3. 访谈与调研设计

第一轮探索访谈：
居民8—12人；社工/社区人员5—8人；每次20—30分钟。
核心问题：最近一次办救助在哪里卡住、使用了哪些渠道、理解哪些条件最困难、准备材料花了多久、是否愿意使用预筛系统、对隐私最担心什么。

第二轮原型可用性测试：
居民15—20人；工作人员5—10人。
任务：用传统官网和本系统分别完成同一虚构案例，比较完成时间、遗漏数、错误数、主观易用性。

记录方式：知情同意、匿名编号、任务用时、点击路径、错误点、SUS量表、开放反馈。不得录入真实疾病和身份证原件，除非有明确书面同意和安全方案。

4. 需求优先级

Must：地区/日期识别、家庭问卷、5类救助预筛、条款证据、材料清单、政策版本控制、拒答与转人工、管理员规则审核。
Should：自然语言对话、OCR材料预检、组合救助、反事实解释、政策更新预警、长者友好模式。
Could：语音输入、多方言、跨城市迁移、社区端批量工作台。
Won't（首版不做）：官方申报、自动审批、救助金精确承诺、13个事项全部深度判断、真实政务数据接口。

四、场景范围与MVP边界
============================================================

1. 地域范围

MVP只覆盖广州市。输入地区不是广州时，系统只给通用说明和官方渠道，不执行本地资格判定。

2. 时间范围

每次判断必须包含query_date。默认当天，但用户可以回溯日期。规则选择条件为：
effective_from <= query_date <= effective_to（若effective_to为空则视为未设置结束日期），且地区和文件状态匹配。

3. MVP五类事项

（1）低收入人口认定与监测；
（2）最低生活保障；
（3）最低生活保障边缘家庭救助；
（4）刚性支出困难家庭救助；
（5）临时救助。

第二阶段再扩展医疗、教育、住房、危房、失业登记、就业困难认定。这样既能覆盖核心痛点，又能让三人团队把算法、测试和产品做深。

4. 三个主演示场景

场景A：用户不知道该申请什么。
输入：“广州户籍，三口之家，父亲失业，母亲月收入，孩子在读，近期有大额医疗支出。”
输出：可能相关的低保/低保边缘/刚性支出困难/临时救助组合、需要补问的字段、每项依据。

场景B：政策跨版本。
同一家庭分别以2026-07-31和2026-08-01查询。系统自动选择不同版本，显示旧文件被替代关系；普通RAG基线可能混用条款，形成直观对比。

场景C：材料不完整或互相矛盾。
用户上传已脱敏的合成材料。OCR识别家庭成员、日期、收入等字段，发现缺失页、过期证明、姓名/金额不一致，只提示核验，不认定材料造假。

五、完整业务流程
============================================================

居民端流程：

步骤1 选择地区和查询日期。
步骤2 阅读隐私说明，选择“快速问卷”或“描述我的情况”。
步骤3 大模型把自然语言转成家庭画像草稿；用户逐字段确认。
步骤4 动态问卷只追问对候选事项有信息增益的字段，减少无关问题。
步骤5 时态规则引擎计算每个事项的TRUE/FALSE/UNKNOWN条件。
步骤6 组合救助规划器对候选事项排序，避免互斥/重复，标记关联事项。
步骤7 展示三态结论：可能符合、目前可能不符合、信息不足。
步骤8 展示“为什么”：已满足条件、未满足条件、待补充信息、原文条款、政策版本。
步骤9 生成个性化材料清单；用户可选择上传合成/真实材料做预检。
步骤10 提供线上官方入口、线下窗口、电话、时限和导办清单下载。
步骤11 用户可反馈“有帮助/不准确”，错误进入人工复核队列。

工作人员端流程：

步骤1 建立匿名咨询编号。
步骤2 录入或导入家庭画像，不录入无必要身份信息。
步骤3 查看候选救助、规则路径和证据。
步骤4 对UNKNOWN项进行补问，对冲突项转人工。
步骤5 导出咨询摘要，明确标注“辅助导办，不作为审批依据”。

管理员端流程：

步骤1 录入/抓取新政策并计算页面哈希。
步骤2 AI抽取条款、实体、阈值、生效区间和替代关系，生成规则草稿。
步骤3 两名审核人独立比对原文，第三人裁决分歧。
步骤4 运行历史案例回归测试。
步骤5 只有测试通过且审核状态为verified的规则才可发布。
步骤6 旧规则不删除，改为superseded或expired，以支持历史查询。

六、核心AI与算法设计（国赛创新重点）
============================================================

创新1：Policy2Rule时态政策编译器

目标：把政策自然语言转为“机器可执行、人工可检查、版本可回滚”的规则，而不是把整篇PDF塞进向量库。

处理链：
文档解析 -> 章节/条款切分 -> 规则相关性分类 -> 实体与数值抽取 -> 条件/例外/结果关系抽取 -> 生效与替代关系识别 -> 规则DSL草稿 -> 双人复核 -> 单元测试 -> 发布。

规则示意（非正式政策结论）：
RULE R-DIBAO-INCOME-2026
WHEN region.city == “广州市”
AND query_date >= 2026-08-01
AND per_capita_adjusted_income <= annual_parameter.dibao_standard
AND asset_rules == TRUE
THEN condition.income_eligible = TRUE
EVIDENCE source_id=GZ-002/GZ-003, article=对应条款

关键创新点：
（1）规则不是单一值，而是“地区 + 时间 + 条件 + 例外 + 证据”的对象；
（2）旧政策不删除，建立supersedes边；
（3）发布前自动执行回归案例，发现新规则对既有结果的影响；
（4）LLM只生成草稿，未审核规则绝不能进入生产判断。

可实现模型：小型中文指令模型做信息抽取，结合正则和词典抽取金额、倍数、日期；用LoRA微调条款分类/规则槽位抽取。4060显存不足时使用4bit量化7B/8B模型或更小模型，训练任务拆成分类、NER和结构化生成。

创新2：规则引擎 + RAG + 大模型的三层可信推理

第一层——确定性规则引擎：负责资格条件、阈值计算、时间和地域选择。
第二层——混合检索RAG：BM25关键词检索 + 向量检索 + 重排，查找定义、材料、流程和解释性条款。
第三层——大模型：负责理解口语、生成补问、把结构化结论解释成易懂文字。

强约束：
（1）大模型不能改写规则引擎结果；
（2）答案中的政策事实必须来自retrieved_evidence；
（3）没有证据就不生成具体结论；
（4）每一项结论显示source_id、条款和有效日期；
（5）规则与文本检索冲突时停止判断并进入人工复核。

创新3：三值资格逻辑与“不确定性优先”

每个原子条件只取TRUE、FALSE、UNKNOWN：
TRUE：输入和材料足以支持条件成立；
FALSE：有明确证据表明条件不成立；
UNKNOWN：缺少必要信息、OCR置信度低、政策冲突或规则未覆盖。

事项结论：
所有硬条件TRUE -> “可能符合，建议申请”；
存在硬条件FALSE -> “目前可能不符合”，同时显示原因；
无FALSE但存在UNKNOWN -> “信息不足，需要补充”；
政策过期/冲突 -> “无法自动判断，请咨询官方”。

这样可以把高风险“假阳性”压到最低。系统永远不用“您一定符合/一定获批”。

创新4：基于反事实的最小补充解释

普通系统只说“不符合”。本系统计算“要让预筛结果从FALSE/UNKNOWN变为可申请，最少需要补充或核实哪些信息”。

方法：把规则表达为约束图；对失败路径计算最小代价条件集合。代价按信息敏感度、获取难度和用户操作成本加权。只输出可补证/可核实的事实，不建议用户改变或隐瞒真实情况。

示例：
不是“把收入降到某值就能申请”，而是“目前缺少共同生活成员范围和近6个月收入证明，无法计算人均收入；补齐这两项后可继续预筛”。

创新5：组合救助规划图

救助并非单一事项。建立Benefit Graph：
节点：低保、低保边缘、支出型困难、临时救助、医疗、教育、住房、就业等。
边：前置认定、可联办、互斥、可并行、可能免申即享、需线下办理。

排序得分：
Score(b) = w1*EligibilityConfidence + w2*NeedCoverage + w3*Urgency + w4*EvidenceCompleteness - w5*ApplicationCost - w6*ConflictRisk

急难事件优先提示临时救助；长期低收入同时展示长期救助；医疗支出触发第二阶段关联事项提示。得分只决定展示顺序，不替代政策判断。

创新6：材料OCR与跨文档一致性核验

技术链：首版已采用RapidOCR/ONNX Runtime完成图片文字识别、内容类型辅助分类和日期/金额候选抽取；下一阶段再加入PDF页级解析、复杂版面分析、跨文档实体对齐与规则需要材料映射。

可检查：
（1）必需材料是否齐全；
（2）页数/关键区域是否缺失；
（3）姓名、日期、金额、家庭成员数量是否一致；
（4）证明是否过期；
（5）图片是否模糊，是否需要重拍。

系统只说“存在不一致，请核对”，不能说“疑似造假”。

创新7：政策更新影响分析

新文件进入后，系统输出：新增规则、删除规则、阈值变化、适用对象变化、替代文件、受影响测试案例数量。用2026年低保新旧政策切换做演示。

七、数据工程设计
============================================================

1. 数据层级

Bronze原始层：政府网页、PDF、下载时间、URL、SHA-256，不修改原文。
Silver条款层：清洗后的章节、条款、表格、发布机关、文号、生效日期、地区、状态。
Gold规则层：人工复核的规则DSL、材料映射、事项关系、评测案例和标准答案。

2. 主要数据库表

policy_document：doc_id、title、issuer、doc_no、region、publish_date、effective_from/to、status、source_url、hash。
policy_clause：clause_id、doc_id、article_no、clause_text、topic、embedding、page/position。
policy_relation：source_doc、target_doc、relation_type（supersedes/amends/references）、evidence。
benefit_item：benefit_id、name、department、deadline、channel、scope。
policy_rule：rule_id、benefit_id、version、logic_json、status、priority、effective_from/to。
rule_evidence：rule_id、clause_id、quote_span、review_state。
required_material：material_id、benefit_id、condition、validity_period、required_level。
office_directory：district、office、phone、address、verified_at。
case_profile：匿名家庭画像；真实环境加密且设置TTL。
screening_result：三态结论、规则版本、证据、耗时、人工覆盖记录。
evaluation_case：输入、查询日期、专家标签、困难类型、数据来源、版本。
feedback：匿名评分、问题类型、是否进入复核。

3. 首版数据规模目标（均为计划值）

官方原始文档：已保存11份，后续扩展至30—50份。
条款级语料：800—1500条。
人工复核核心规则：100—200条。
合成家庭案例：800个。
专家/工作人员复核案例：至少100个。
匿名真实咨询问题：争取50个；拿不到时如实说明，不伪造。
OCR合成材料：每类文档100—200张，通过模板扰动生成，不能使用真实身份证公开展示。

4. 案例构造原则

（1）普通案例、边界案例、缺失案例、矛盾案例、过期政策案例保持分层；
（2）阈值上下1%、5%、10%必须覆盖；
（3）训练/验证/测试按政策文件、规则簇或时间切分，避免同模板泄漏；
（4）合成样本明确标记synthetic，不与真实成效混淆；
（5）由两名成员独立标注，Cohen’s Kappa作为一致性指标，分歧交第三人裁决；
（6）关键测试集冻结，开发人员不能边看测试答案边改提示词。

5. 数据更新机制

每日/每周任务检查：页面可访问性、Last-Modified、正文哈希、标题和文件状态。
检测变化后：创建新草稿版本 -> AI差异摘要 -> 人工审核 -> 回归测试 -> 发布。
有效期前30天：管理员首页红色预警。
来源失效或无法核验：相关规则自动降级为needs_review，居民端不做强结论。

八、系统架构与技术选型

1. 推荐架构

前端：Vue 3 + TypeScript + Vite + Element Plus（团队若更熟React，可换React，不影响方案）。
后端：FastAPI + Pydantic + SQLAlchemy。
数据库：PostgreSQL + pgvector；开发期可用SQLite，但国赛演示建议PostgreSQL。
缓存/任务：Redis + RQ/Celery，用于OCR和离线索引。
对象文件：本地加密目录或MinIO；首版无需云对象存储。
检索：PostgreSQL全文/BM25组件 + pgvector + reranker。
规则引擎：自研JSON DSL解释器，Python Decimal做金额计算，禁止float处理金额。
OCR：首版RapidOCR/ONNX Runtime；复杂版式与PDF页级处理可评测后再引入PaddleOCR/PP-Structure。
模型服务：量化中文7B/8B指令模型；embedding可用BGE-M3类模型；reranker使用轻量中文重排模型。
部署：Docker Compose，一键启动；Nginx反向代理；演示环境可全部离线运行。
监控：结构化日志 + Prometheus/Grafana可选；首版至少实现请求ID、模型版本、规则版本、耗时和错误码。

2. 4060资源预算

显存按8GB保守设计：
量化LLM 4bit：约4.5—6GB；
Embedding/Reranker不与LLM同时常驻，或转CPU/分时加载；
OCR按任务队列串行/小批处理；
LoRA训练选择小模型、短序列、gradient checkpointing和小batch；
演示时不进行训练，只运行推理。

如果4060是显存更大的版本，可增加并发，但方案不依赖这一点。

3. 服务划分

api-gateway：鉴权、限流、请求ID。
profile-service：家庭画像与动态问卷。
policy-service：文档、条款、版本、来源。
rule-service：规则求值、追踪、反事实。
retrieval-service：混合检索与重排。
llm-service：结构化抽取、补问和受约束解释。
document-service：OCR、材料类型、字段校验。
planner-service：组合救助排序。
admin-service：审核、发布、回归测试、更新告警。

三人团队不需要真正拆成网络微服务。推荐代码层按以上边界模块化，部署为“模块化单体 + 独立模型工作进程”，降低运维复杂度。

九、关键接口设计
============================================================

POST /api/v1/profile/parse
输入：自然语言描述、地区、查询日期。
输出：结构化家庭画像草稿、每字段置信度、待用户确认字段。

输入：HouseholdProfile、候选事项可选。
输出：screening_id、每事项三态结论、满足/失败/未知条件、规则版本、证据ID。

GET /api/v1/screenings/{id}/explanation
输出：通俗解释、原文条款、政策链接、最小补充项、官方免责声明。

POST /api/v1/documents/precheck
输入：文件、文档类型、用户同意标记。
输出：清晰度、字段、置信度、缺失页、不一致项、建议；原文件按TTL删除。

GET /api/v1/benefits/{id}/materials?region=&date=
输出：条件化材料清单、是否必需、有效期、来源。

GET /api/v1/offices?district=
输出：主管部门、电话、地址、最近核验日期。

POST /api/v1/admin/policies/ingest
输入：URL/文件。
输出：文档元数据、差异、抽取规则草稿；仅管理员可用。

POST /api/v1/admin/rules/{id}/verify
输入：审核意见和电子签名标识。
约束：提交人与第二审核人不能相同。

POST /api/v1/admin/releases
约束：所有P0回归测试通过才允许发布。

统一返回字段：request_id、data、warnings、policy_snapshot、model_version、created_at。

十、前端页面与交互设计
============================================================

1. 首页
三个大按钮：“帮我看看能申请什么”“检查材料”“查询政策依据”。展示官方边界声明和隐私承诺。

一次只问一个问题；显示进度；支持“不清楚”；解释为何需要该信息；敏感字段旁显示用途和保存时间。

避免红绿颜色作为唯一信息，兼顾色弱用户。

5. 材料中心
个性化清单、上传预检、模糊/缺页/不一致提示、原文件删除倒计时。

大字号、高对比、语音朗读、少输入、多选择、可打印一页式导办单。语音识别可作为加分项，不作为MVP阻塞项。

7. 管理后台
政策版本时间轴、差异视图、规则草稿、双人审核、回归测试结果、即将过期文件、用户错误反馈。

十一、安全、隐私与伦理设计
============================================================

1. 数据最小化
资格预筛优先使用年龄段、收入区间、匿名成员标识，不默认收姓名和证件号。只有材料预检时临时读取图像。

2. 分级分类
公开数据：政策、办事指南、窗口地址。
一般业务数据：匿名问卷、系统日志。
敏感个人信息：身份证、疾病、收入、财产、联系方式；默认不进入训练集。

3. 安全措施
传输HTTPS；数据库敏感列加密；文件随机token命名；访问控制RBAC；管理员双因素认证可选；日志脱敏；下载和审核留审计记录；上传文件限制类型/大小并做恶意文件检查。

4. 保存策略
游客模式不保存家庭画像；注册试用默认7天删除；上传原件处理完成后尽快删除，最长时间在隐私说明中明确；模型训练数据与业务数据物理/逻辑隔离。

5. 模型安全
政策文档视为数据而非指令，抵御提示注入；工具调用白名单；输出结构JSON Schema校验；证据缺失拒答；禁止模型生成身份证、伪造材料或规避审核建议。

6. 公平性测试
在其他条件相同时，对性别、年龄表达方式、城乡表述等做成对测试；结果不应因无关属性改变。地区差异只能来自明确政策规则。

7. 人在回路
高风险结论、政策冲突、OCR低置信度、涉及急难或人身安全的场景均转人工/官方热线。系统显著展示“预筛不等于审批”。

十二、测试与实验设计
============================================================

1. 必须对比的基线

B0 关键词搜索/BM25。
B1 纯向量RAG。
B2 大模型直接读政策回答。
B3 只有规则引擎。
B4 完整系统：时态规则 + 混合检索 + 大模型解释 + 反事实。

2. 核心指标与目标值（目标，不得提前写成结果）

政策检索 Recall@5 >= 0.90；
证据引用准确率 >= 0.95；
5事项资格预筛宏平均F1 >= 0.90；
高风险假阳性率 <= 0.02；
UNKNOWN识别F1 >= 0.85；
政策版本选择准确率 = 1.00（这是硬门槛）；
规则执行确定性：同输入、同快照100%同结果；
材料分类准确率 >= 0.95；
关键字段抽取F1 >= 0.92；
跨材料矛盾检测F1 >= 0.90；
有事实性政策陈述但无引用的比例 <= 0.03；
单用户本地推理P95 <= 12秒；
系统可用性SUS >= 80；
相对传统官网任务完成时间下降目标 >= 40%。

3. 测试集构成

普通案例30%；阈值边界20%；信息缺失15%；冲突信息10%；政策换版10%；跨地区5%；急难情形5%；对抗/提示注入5%。

4. 消融实验

去掉时态选择：观察旧政策误用率。
去掉规则引擎：观察资格幻觉和假阳性。
去掉重排器：观察证据召回和引用准确率。
去掉反事实模块：观察用户一次补齐信息率和任务时间。
去掉OCR一致性核验：观察材料遗漏/冲突发现率。

5. 关键单元与性质测试

（1）金额统一使用Decimal，测试0、负数、极大值、四舍五入；
（2）家庭人数不能为0；
（3）收入增加且其他不变时，不应让基于收入上限的资格从FALSE变TRUE（除非明确政策例外）；
（4）查询日期跨过生效日时，必须切换规则快照；
（5）旧规则标记superseded后不能用于当前查询，但仍能用于历史回放；
（6）缺少硬条件时不能输出“可能符合”；
（7）任何展示条款必须能回到原始文件；
（8）模型服务宕机时，规则预筛和官方链接仍可用，解释降级为模板。

6. 专家复核流程

从冻结测试集抽取100—150例，邀请社工/社区工作人员/相关法律或公共管理教师独立判断。若无法取得民政专业人员支持，应在论文和答辩中明确“专家构成”，不把同学互审包装成权威专家标签。

7. 应用效果实验

采用交叉实验：A组先官网后系统，B组先系统后官网，降低学习效应。
测量：是否找全事项、材料遗漏数、错误政策引用数、任务时长、求助次数、SUS和信任度。
统计：报告均值/中位数、95%置信区间、效应量；样本少时不夸大显著性。

3:40—4:00 应用与边界
展示试用反馈/合作证明、推广到其他地区的方法，最后再次说明“辅助导办，不替代审批”。

十七、评委高频问题与回答要点
============================================================

Q1：政府已经有“一件事”，你们为什么还要做？
A：官方平台解决申报和跨部门联办，我们解决申报前的信息不对称：主动发现候选事项、解释资格缺口、一次备齐材料、识别政策版本，并把用户导回官方渠道。二者是前后衔接，不是重复建设。

Q2：这不就是RAG吗？
A：RAG只负责检索解释。资格预筛由带地区和生效区间的规则引擎执行；Policy2Rule将条款变成审核后可运行规则；反事实算法生成最小补充项；政策更新通过回归测试发布。可展示纯RAG与完整系统在换版和阈值案例上的差异。

Q3：AI答错导致群众损失怎么办？
A：三值逻辑、证据约束、假阳性优先控制、冲突拒答、人工转接、版本快照和醒目免责声明。系统从不输出行政确认结论。

Q4：训练数据从哪里来？
A：政策语料来自国家、省、市政府公开页面，已保留URL与原始文件；案例以规则约束合成为主，冻结测试集由专业人员复核；真实咨询只在知情同意和脱敏后使用。

Q5：规则为什么需要AI？人工写不行吗？
A：最终发布必须人工审核，但AI把长政策自动切分、识别条件/例外/日期、生成规则草稿和变更影响，显著降低维护成本；算法效果用抽取准确率和人工修订时间量化。

Q6：能否推广全国？
A：平台抽象出统一的家庭画像、规则DSL和事项图，迁移到新城市主要替换地区政策与参数。需要重新审核本地规则，不宣称一个广州模型直接适用于全国。

Q7：为什么只做五项？
A：13项全做会造成浅而不准。五项覆盖核心民政救助，能把资格、时态、材料和证据做深；架构与数据表已支持逐项扩展。

十八、风险清单与止损线
============================================================

R1 找不到政府/社区合作。
缓解：先找校内社会工作、公共管理或法律教师，再联系社区社工站；没有盖章证明也可以用规范访谈和可复现可用性实验，但应用效果分会受限。

R2 政策理解错误。
缓解：只发布双人复核规则；关键规则请专业人员抽查；系统显示原文；争议项标UNKNOWN。

R3 范围过大。
止损线：第8周仍未稳定完成低保和低保边缘的端到端链路，立即暂停OCR和第二阶段事项，先把规则与评测做实。

R4 模型在4060上太慢。
缓解：4bit量化、小模型、模板化解释、模型按需加载；规则引擎不依赖LLM，必要时云端仅作开发对比，正式演示本地可降级。

R5 没有足够真实数据。
缓解：该项目不需要大规模个人数据训练。核心数据是政策与规则；用合成边界案例验证逻辑，用少量真实匿名咨询验证可用性。

R6 数据和结果造假风险。
止损线：所有“提升百分比、准确率、用户人数、合作单位”只有在留下原始记录后才能写入提交材料。计划值必须标“目标”。

R7 临时救助文件临近有效期。
缓解：将其做成过期预警的真实演示；若出现新文件，按版本流程录入，不继续使用旧规则。

二十、最终立项建议
============================================================

建议正式选择本题，并以“AI+场景创新”为主赛道。它符合三人团队、Python/Web能力和单机4060条件，也有清晰的民生价值。

但项目的准确定位应从“社会救助智能问答”改为：

“面向申请前环节的、可追溯可解释的社会救助智能导办与材料预检系统”。

作品的真正核心不是聊天，而是：
政策在什么时间和地区有效；
家庭还缺哪项关键信息；
为什么推荐这些救助；
结论依据哪条政策；
材料是否齐全一致；
AI不知道时能否可靠地停下来。

只要完成上述闭环，并拿到真实的测试与试点证据，这个方向具备国赛级作品应有的社会意义、算法深度、工程完整度和可验证性。
